# Leo — developer user audit, 25 October 2026

**Vote: A — everyday reminders and notes, with an optional, narrowly described developer monitor.** I run three to six Claude Code/Codex sessions a day. I would try Sidefolk as an attention aid while reading, reviewing, or away from my terminal. I would not yet make it my session control plane. B, developer-first, requires considerably stronger session identity and truthful capability boundaries. C, a broad shell, adds another execution surface before the observation and return-to-work loop earns trust.

This conclusion is independent: I did not read the other council reports. I read AGENTS.md, memory/STATUS.md, DECISIONS.md and LEARNINGS.md, then explored the browser preview before inspecting implementation. My observations are browser sample data or explicitly marked source inferences. I made no live model calls, native captures, global-config changes, or user-data changes. The parent reports 100 Vitest and 34 Rust tests passing, three opt-in Rust tests ignored, WebKit sample checks, and a successful 9.27 MiB release build. Those are separate engineering evidence; I did not rerun them or treat them as native workflow verification.

**What I would use.** At `/settings.html`, Today presents one waiting request, upcoming reminders, work sessions, and notes. “Review request” moves into a useful master-detail layout: the request stays alongside other work. The sample command review displays Codex, project `api`, short session `04c1`, exact command and working folder, each with a copy button. Technical details expose the full session and request IDs. Closing the review does not answer. This is a credible improvement over noticing a blocked terminal after fifteen minutes. The value is attention recovery, especially when another app occupies me; terminal execution itself is already available in my usual tools.

The review also respects deliberate interaction: choices are buttons, sending locks the choice, failure offers Retry, and a successful answer remains readable. See [requests.ts](/Users/ghassenbrg/git/sidefolk/src/dashboard/requests.ts:194). The review is readable and restrained; the terminal preview uses the same cream/mint visual language without turning the shell into a decorative toy. I would still expect quiet defaults. Source [hooks.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/hooks.rs:221) deliberately leaves Claude permissions to a frontmost terminal/editor and holds them on the companion otherwise. That is a sound interruption policy, although native focus detection is unverified here.

**Project identity holds better than task identity.** Live agent state is keyed by `source:session`, so two Claude sessions in one repository do not overwrite each other. The rows show tool, repository basename, four-character session prefix, current action, mode, and Open/Review. That separates sessions mechanically, but “Work session 7b3e” is not how I remember a reviewer versus an implementer. There is no task title, branch/worktree label, or host label in the row. Different checkout paths with the same basename also look alike until a permission review reveals the working folder. Source: [ui.ts](/Users/ghassenbrg/git/sidefolk/src/dashboard/ui.ts:98), [agents.ts](/Users/ghassenbrg/git/sidefolk/src/agents.ts:110).

The larger gap is completion history: `outcomes` is a map keyed by project, and each done/failed event replaces that project's previous outcome. Three parallel sessions finishing in one repository become one recently finished result, even though Sessions advertises continuation. This is a direct source finding, not a stress-test observation: [agents.ts](/Users/ghassenbrg/git/sidefolk/src/agents.ts:148). Quiet sessions also disappear after ten minutes without another event ([agents.ts](/Users/ghassenbrg/git/sidefolk/src/agents.ts:194)). For developer-first positioning, “no recent signal” needs different treatment from “nothing running.” Otherwise I must keep checking the terminal to verify the monitor.

**Questions lose the most valuable context.** I simulated an MCP-shaped free-answer question in the preview's in-memory sample store, using the actual metadata shape from `agent-tools.ts`. It rendered Yes, No, and a written answer field correctly. It also rendered “Codex · Work session” without an ID, no working-folder detail, no originating-session Open button, and no countdown. This is consistent with the source: the MCP forwarder carries client and cwd, but no session identity; the app emits question metadata without a session or expiry ([mcp.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/mcp.rs:196), [agent-tools.ts](/Users/ghassenbrg/git/sidefolk/src/agent-tools.ts:41)). Two Codex agents asking from the same repository cannot be reliably distinguished from this information alone. The transport defaults to a 120-second wait, maximum 600, but the person answering is not shown that deadline ([mcp.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/mcp.rs:272)).

Permission expiry has a concrete contradiction. Open the stock Codex request, expand Technical details: it says “9 minutes more, then the tool asks in its own window.” The generic review produces that promise for every source ([requests.ts](/Users/ghassenbrg/git/sidefolk/src/dashboard/requests.ts:120)). Claude's HTTP hook can return control to its own prompt. Sidefolk-owned Codex cannot defer; after ten minutes the driver explicitly declines ([codex.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/codex.rs:379)). I would wrongly postpone a decision expecting a later prompt. Copy has a smaller trust defect: clipboard errors are swallowed and the button still becomes “Copied” ([requests.ts](/Users/ghassenbrg/git/sidefolk/src/dashboard/requests.ts:50)). I did not force a clipboard failure; that is source-supported risk.

**“Connected” currently means configured.** AI tools Settings shows Connected/Not connected and explains backups and setup changes well. However, Claude's check accepts any recognized Sidefolk hook; the MCP check detects a named config entry/table. Neither demonstrates complete hook coverage, a working executable, a reachable app, or that a currently running agent loaded the configuration ([claude_setup.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/claude_setup.rs:79), [mcp_setup.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/mcp_setup.rs:52)). The visible repair route is disconnect/setup, rather than diagnose/test/repair. Native confirmations and backups are good foundations. For my daily workflow I need “configured; last event two minutes ago” and an inexpensive end-to-end check before trusting silence.

Codex needs an explicit capability distinction. External Codex can call the installed notify/ask/remind/presence tools. That registration does not subscribe Sidefolk to all external Codex progress or approvals. The richer path starts Sidefolk's own `codex app-server`, uses one thread per folder, and receives that process's events ([codex.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/codex.rs:49)). New session, however, launches the ordinary CLI in the chosen terminal ([actions.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/actions.rs:138)). I found no equivalent external Codex observation adapter in this path. The individual Settings descriptions are reasonably scoped, but “sessions appear as soon as Claude Code or Codex starts working” is too broad. Owned threads are also created `ephemeral: true`, while Open later proposes `codex resume`; resumability needs proof before promising pickup after restart ([codex.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/codex.rs:189)).

**Opening is host-dependent, not universally exact.** The implementation makes a serious effort: Claude hook connection → process tree → host/tty, skips the bundled CLI app, validates IDs, quotes paths, refuses duplicate resume of a busy owned Codex thread. Terminal and iTerm can select the matching tty/tab. Inside Sidefolk can select its matching PTY. Ghostty, VS Code, Claude desktop and other hosts are brought forward, with the accurate message “Select your session in its window”; the implementation does not select an exact conversation there ([sessions.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/sessions.rs:149)). Detached or ended sessions resume in a new terminal. This is useful partial recovery, but the universal Settings claim “A running session always comes forward where it is” overstates the result. Native Automation permission, tab matching and actual resume are all unknown in this audit.

**Full access is three different mechanisms under one name.** Clicking a running row toggled immediately in preview and toasted “Risky commands still ask.” That toggle persists a Sidefolk auto-answer list and applies regex exceptions to command text; non-command requests pass that filter ([access.ts](/Users/ghassenbrg/git/sidefolk/src/access.ts:22), [companion.ts](/Users/ghassenbrg/git/sidefolk/src/companion.ts:174)). New-session Full access instead selects Claude auto mode or `codex -a never -s workspace-write`. Turning the later Sidefolk switch off does not reconfigure those launch flags. The row state measures Sidefolk's list, not the CLI's actual permission policy. “Asks first” can therefore describe the wrong guarantee. I want explicit modes per backend, actual policy visibility, and a clear limit to the risky-command heuristic before using unattended work.

**Embedded terminal is convenient but not the differentiator.** `/settings.html?tab=terminal` clearly says “Preview: no shell runs here.” Source uses a real login shell/PTY, a one-megabyte in-memory output buffer, xterm tabs retained across view changes, and an explicit close warning. Tabs use `command · folder`, so several Claude sessions in one folder repeat the same title ([inside.rs](/Users/ghassenbrg/git/sidefolk/src-tauri/src/inside.rs:68)). This supports window reopen within the running app; it is not persisted terminal restoration after app restart. Real CLI rendering, keyboard shortcuts, process shutdown, and reconnect behavior remain native hand checks.

I would ship A with an opt-in Claude monitor whose promises match the supported hosts, plus scoped Codex companion tools. B earns my vote only after multiple same-repo completions survive, every question identifies its session and deadline, connection health is observable, and permission/open behavior is accurate per backend. For a three-to-six-session developer, those four improvements matter more than another command launcher.
